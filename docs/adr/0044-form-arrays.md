# ADR 0044 — Arrays of the form: items that keep a key, states rewired to them, and two states built when first read

- Date: 2026-11-10
- Status: accepted (design choices delegated by the owner, reported for review; `@experimental` until the go/no-go decision of T2.7 and the frozen contracts)

## Context

ARCHITECTURE.md §7.11 asks of the form's arrays that each element have a stable identity, a business key or a generated one, and that issues and states be attached to it, not to its index, so that they follow it when it moves; §5.3 gives the `{ key }` segment for that. T2.4 b asks for `array`, insertion, removal and moves, a property that a moved element keeps its issues, and the heap of an item measured on a thousand items, deciding whether the states of a node should be built when first read (ADR 0043 measured 1.65 kB per field).

Two records constrain the design. ADR 0041 names every dependency of a derived node at construction, and leaves to this step whether "a list that grows is a source holding the list or a node built again with it"; ADR 0042 forbids a computation to read the graph. The states of an array that follow its items (its raw value, `touched`, `pending` from below, the issues of its descendants, its parsed value) depend on nodes that come and go: with fixed dependencies, neither option of ADR 0041 works alone. A node built again leaves the nodes that read the old one behind, and its listeners with them; a source holding the list of values cannot reach the states that the items' own schemas give.

The references, read in their shipped code and run on 2026-11-10 (Angular Signal Forms 22.2.4, TanStack Form 1.33.5):

- **Angular** follows the very objects of its model: it writes a hidden symbol onto each item object (`_validation_errors-chunk.mjs`, lines 1179-1180), so that a node and its state move with the object. A list of new objects, as a server or a draft gives back, rebuilds every node and loses its state; a frozen item throws; primitives are tracked by index; the same object twice shares one node. An item is named by its index (`keyInParent`), which changes when it moves. There is no array API: the application writes the model. Its errors are computed again from the data.
- **TanStack** keeps its field states by path and shifts them by index (`metaHelper.js`): a move or a removal takes the touched state, the errors and the dirty flag along. An insertion shifts them only after a validation it awaits, so that on return the state sits on the wrong row, and the validation then marks the new row and every row after it touched; a nested array is shifted wrongly (`metaHelper.js`, line 122, only the first `[n]`). There is no key option; its React guide keys rows by index. `isDefaultValue` compares the list with the default deeply; `isDirty` stays set.

## Options

1. **Native, or do nothing.** The platform has no list of form states. Rejected.
2. **Follow the objects of the value, as Angular does.** It writes into the application's objects, fails on frozen ones, loses every state on a list of new objects, and cannot follow primitives. Rejected.
3. **Shift states by index, as TanStack does.** Every structural write walks and renames the state of every row after it, which TanStack gets wrong for insertions and nested arrays; paths of issues change with the order. Rejected.
4. **A list owned by the array: one source of values, each item a view of it.** Writes become copies of the list, every item's view runs again on every write, and the states that the items' own schemas give still need dependencies that change: a second implementation of the tree. Rejected.
5. **Rebuild an array's nodes, and its ancestors', when its items change.** The public nodes would be replaced under their listeners. Rejected.
6. **Items as nodes of the tree, each keeping a key; the states of the array that follow its items rewired to them when they change, by a new function of the core's graph (kept).**

Within option 6, for the graph:

- **A node whose dependencies come from a source of nodes ("join").** Natural, but its dynamic dependencies live in the refresh that every node runs: bytes in `yaltaan/core-reactive`, which has 8 to 15 left of its 1,000. Rejected.
- **`rewire(node, deps)`, a function beside `createGraph` (kept).** It replaces the dependencies of a derived node as a write does, from outside any computation: the node and its watched dependents marked, its listeners queued, the batch respected; refused with a `TypeError` when a new dependency reaches the node, by a walk that stops at the old dependencies, which cannot reach it, so that the graph stays acyclic as §5.5 requires. It computes nothing itself: the first version refreshed the new dependencies to watch them, and the laws of the form caught a schema asked, inside a batch, for a value half written; nodes that start being watched are marked stale instead. A node rewired may depend on nodes created after it, so that listeners, called by creation order of their nodes, are no longer always called in a topological order; values are not affected, each node refreshing its dependencies first. Exported as a function, it is shaken out of an application that does not call it.

For the form:

- **Keys.** Every item takes a key of the form, the next integer from 0 in the order it builds items (deterministic, so that a page rendered on a server and in a browser agree), kept for its life at the end of its path (kept). With `identity`, the path of a business key in an item, as `each` of `@yaltaan/rules` names it, writes and issues find an item by the key its value holds at that time: `set` and `reset` keep the item whose value holds the key of each value, `insert` refuses a key a value holds, a `{ key }` segment of an issue names the item whose value holds it. A blank key (`undefined`, `null`, `''`, an empty list) or one given twice is refused with a `TypeError`; keys compare by SameValueZero on their first 16,000 code units, as `rules` compares them, since V8 hashes longer strings by their length. The first version made the business key, read once, the key of the item's path: the contradictor below found that once the key field was edited, `insert` and `set` compared two different keys, the form's own raw value no longer wrote back, and a new item could take the old key and share its path with another. A business key with a generated one for blank values was rejected too: the two kinds could collide, and a `{ key }` segment would be ambiguous.
- **Paths.** An item's path ends with `{ key }`; an issue that a schema places through an array names the item by its index in the very value it read (the array keeps, for each raw value it composes, the items it was composed from), or by a `{ key }` segment, and the index is replaced by the item's `{ key }`, so that the path of an issue starts with the path of its node and stays the same when the item moves. The issue's `cause`, the schema's own issue, keeps the index it gave: an item moved under a schema of the list sees its issues change by that cause.
- **Writes.** `insert(index, raw?)`, `remove(item)`, `move(item, index)`: by the item, not its index, so that a view that kept an old index cannot remove another row; `remove` and `move` return whether the item was there. `set(list)` keeps items by position, or by key with `identity`; a value left builds an item, an item left is removed. `reset(list)` does the same and makes those items the ones `reset()` gives back, in their order, each given back its value of that reset, the array's initial list taken from them. A write reads its whole value and checks it before it writes anything.
- **dirty.** The raw value of the array against its initial list, item by item with the comparisons of its fields (kept), TanStack's `isDefaultValue`: a row moved makes the list dirty, moved back it is not, and a row removed then added again with the same values leaves it clean. Comparing which items are there (identity) was rejected: a list set back by position to its first value would stay dirty.
- **Conditions.** A condition inside an item reads a field of the same item through `{ key: undefined }`, `anyElement` of `rules`, resolved to the item that holds the node when it is built; every path is checked against the description when the form is built, and a path into another item, or through an array that does not hold the condition, is refused then. The first version resolved a condition of an item only when an item was built: a bad path passed `createForm`, and a `set` building items could fail half way through its batch.
- **Limits.** At most `maxLength` items per array, 1,000 by default, and at most `maxItems` items read by one write, every array of its value counted, 10,000 by default, an option of `createForm`: past either, the write throws a `RangeError` and writes nothing, since a draft or a server answer can hold any length. `maxLength` alone was the first version: nested arrays multiplied it, and the contradictor built a million items through one `set`.
- **What a form without an array pays.** Everything only arrays do is in a class that the spec `array` builds carries, so that a bundler drops it from an application that does not import `array`.

The heap of an item decided one more thing: `dirty` and `parsed` are built when first read (kept), since a view rarely reads either on every field; building every state when first read was not done, its gain smaller once a view reads raw values, issues and touched states, and its cost in code larger.

## Measurements

With a schema on each item: 12,797, 14,601 and 20,062 B before, 9,362, 11,167 and 16,628 B after. A field of a flat group of 20,000 fields: 1,653 B built in ADR 0043, 1,693 B with arrays, 1,019 B once `dirty` and `parsed` wait for their first read, 1,711 B with every state read, 2,361 B with three watched.
- **Size**, `node scripts/size-report.ts`: `yaltaan/form-realistic`, which holds no array, 5,950 / 5,978 B brotli (esbuild / Rollup), from 5,347 / 5,372: 1,551 / 1,566 B more while arrays were in the code every form loads, 458 / 468 once they were reached only through `array`, of which 57 for `dirty` and `parsed` built when first read, then 143 / 138 for the fixes of the review (conditions checked when the form is built, `maxItems`). - **Type cost**, `node scripts/type-cost.ts`: the usage `form` 17,470 / 17,494 instantiations under TypeScript 7 (exact / loose), from 16,828 / 16,852, and 12,037 / 12,058 under 6.0, from 11,719 / 11,740, under their ceilings of 17,700 and 12,300: the conditional types of the specs have one branch more. A new usage, `form-array` (lines kept by reference, a schema of each and of the list, a field disabled through its item, an item read, inserted, moved and removed, a function generic over any array): 19,158 / 19,182 and 12,535 / 12,556; check time +638.3 % and +694.1 % in two runs with it in each of the 2,000 files, budget +900 %.
- **Laws of the graph** (`properties.test.ts` of the core): the random programs now rewire derived nodes to any nodes; per 1,000 programs about 2,900 rewires and 1,260 refused for closing a cycle, judged by a naive model evaluated dependencies first, with no computation during a rewire and none on a batch still writing. **Judge**: preact's `computed` reading a signal that holds its list of nodes, rewired by a write of that signal: 777 of 1,000 programs compared as they are, the rest by the differences already recorded.
- **Laws of the form** (`properties.test.ts`): the naive model holds arrays of fields, groups and arrays, kept by position or by key, schemas on items, on arrays and on groups, answering at once, later, or through `parse` with `{ key }` segments, conditions through items; programs insert, remove, move, set lists that reorder, keep, build and drop items, reset, restore, batch and settle late answers. After each step every state of every node, the path of every node, the key of every item and the cause of every issue are the model's; each schema was asked once per value; each listener was called exactly when its state changed. 400 programs of every shape (one run: 2,553 validations, 142 answers settled late, 149 rejections, 7,588 notifications, 878 writes refused, 164 moves) and 200 crowded with moves of items holding issues (568 moves outside batches, 487 of items that held issues), in about 2 s. Found while writing: the eager refresh of `rewire` above; an item written then removed in one batch, which its listeners still read once, as the model now expects; the `cause` of an issue moved with its item.
- **Examples** (`array.test.ts`): keys, moves under a schema of each item (not asked again) and of the list (asked again, its issue on the same item), writes by position and by key and what they refuse, long keys, the errors of `insert`, `remove` and `move` and their order, `dirty` with a field's `equals`, reset and restore, conditions through items and nested arrays, `{ key }` segments and indexes past the end, a removed item and its late answer, laziness, two structural writes of a batch, scale (250 against 2,000 items), types.
- **References** (`tests/interop/form-arrays.mjs`, outside the gate): the same moves, insertions and removals on Angular Signal Forms 22.2.4, TanStack Form 1.33.5 and the form; asserted where they agree (an item's state and issues follow it) and where the form departs (a path that keeps its key, a list of new objects that keeps its items, an insertion done when it returns, no row touched by it).
- **Mutations by hand**, each run on a copy, restored by copy, against an unmutated control that stays green (515 tests): 54 on `array.ts`, `node.ts` and `rewire`, among them each state not rewired, an issue placed by today's index, a path not rewritten, keys matched by position, by the stored key or by `===`, the bounds off by one, a restore of the current items, a cycle not refused, a walk without its memory (exponential), an old dependency kept, a node held without being marked. 4 survived at first (`dirty` and `parsed` built again at each read, `NaN` keys, a path through an array that does not hold the condition): each now has its test, and the 54 are caught.
- **Contradictor**: a fresh reviewer, given only the question and the code (149,555 tokens), ran a differential test of its own (a form built anew from each raw value as oracle, 3 × 300 programs of 25 steps: no difference), measured leaks (none) and costs (linear, 500 against 4,000 items), and 63 mutations of its own, 10 of which survived, 2 probably equivalent. Verdict: accept with fixes, all applied before this record was committed:
  - `maxLength` bounded each array and not the form: 1,000 × 1,000 nested items through one `set` took 2.4 s and 923 MB. `maxItems` above;
  - business keys read once and compared two ways (above): the keys of paths are now always the form's;
  - `reset()` after an item's own `reset(raw)` contradicted its documentation, which now says that the restored values become the array's initial list;
  - `rewire` is not checked by the types (a compute meant for one value receives others), `identity` is an untyped path, the 16,000 code units were not in the documentation of `identity`, `insert(index, undefined)` takes the element's initial value: the documentation says each, as `reset(undefined)` already does;
  - its 8 surviving mutations that were not equivalent each have a test now (a source no listener watches, an empty list as a key, `-0`, long keys kept and named, a hole read through its prototype, condition paths with a key or an index).

## Decision

Option 6.

- **Core**: `rewire(node, deps)` in `@yaltaan/core/reactive`, as described above; `TypeError` for a source, a foreign node, a dependency of another graph, a cycle, and a call from a computation; nothing changed then.
- **API**: `array(element, { initial, identity, maxLength, schema, disabled })`; an array node holds `items` (a `ReadableNode` of the list of items), `insert(index, raw?)`, `remove(item)`, `move(item, index)`, beside what every node holds; an item is the node of its element and its `key`, a number; `createForm` takes `maxItems`; `ItemOf<E>`, `ArraySpec`, `ArrayOptions` and `ArrayNode` are exported types.
- **Keys, paths, writes, dirty, conditions, limits**: as kept above.
- **States**: `dirty` and `parsed` of every node built when first read.
- **Budgets**: `yaltaan/form-array` gets the hypothesis 8,200 B brotli, about a tenth above its measure, until the pilot is measured against Angular Signal Forms alone (T2.6); the usage `form-array` gets the ceilings 21,200 (TypeScript 7) and 13,900 (6.0), the measure plus a tenth rounded up to the hundred, as ADR 0033, 0038 and 0043 set theirs; `form-realistic` keeps 7,000 B, and the usage `form` 17,700 and 12,300.

## Consequences

- The form's source is split in three modules: `node.ts` (fields, groups, building, wiring, writes), `array.ts` (what only arrays do) and `index.ts`, which re-exports; the module of arrays reaches the other one, never the reverse at run time.
- A structural change costs O(n) per state rewired (n = items), and the walk that refuses a cycle visits what the new dependencies depend on: for the issues of an item, its ancestors' raw values, so O(N) of the form once per change.
- Two structural writes of one batch that give an array back its items still give it a new raw value, told once to its listeners, and its schema is asked again: the list of items changed twice. Avoiding it would cost a node per item.
- A removed item keeps its own states and is read by no state of the form; the answer of its schema that settles later changes nothing in the form. Aborting its validations is T2.4 c's.
- The issues placed through an array carry the form's `{ key }` in their path: a server that knows only indexes reads them back through `toStandardIssue` with `resolveKey`, as for rules; one that knows business keys reads them from the item's value.
- `rewire` trusts its caller with the types: a compute rewired must accept any number of values.
- What the judges do not see: a field inside an item with a schema of its own (its value would not tell the laws which item asked; the examples hold it), `equals`, `NaN` and `-0` in arrays (examples), the listeners of an item once removed, how a view renders a moved item, and the time of a structural write beyond the scale test.

## Review condition

The pilot (T2.5, T2.6) needing an item whose key changes, an array of primitives kept by value, or an API by index; the heap of an item over a budget T2.6 sets; `yaltaan/form-array` over 8,200 B or `form-realistic` over 7,000 B; listeners that need a topological order after a rewire; TC39 Signals reaching Stage 3, whose computed signals track what they read; T2.4 c needing the items' validations aborted on removal in a way `rewire` cannot give.

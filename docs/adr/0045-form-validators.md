# ADR 0045 — Validators of the application in the form: a signal per run, a gate on the schemas, an abort on removal

- Date: 2026-11-11
- Status: accepted (design choices delegated by the owner, reported for review; `@experimental` until the go/no-go decision of T2.7 and the frozen contracts)

## Context

ARCHITECTURE.md §7.11 asks that each asynchronous validation carry a generation token and an `AbortSignal`, that a result whose token is no longer current be ignored, that removing a node abort its validations, and that `pending` be derived. ADR 0043 gave the form schemas that may answer with a promise, the promise of one read standing for the generation; the Standard Schema interface takes no signal, so it left to T2.4 c the validators of the application, their signal, the abort of a removed item's validations, and the interleavings of `fc.scheduler()`. A new option of every node and the object it hands to the application are public API: they need a record.

The references, read in their shipped code and run (Angular Signal Forms 22.2.4, TanStack Form 1.33.5, on 2026-11-11):

- **Angular**, `validateAsync(path, { params, factory, onSuccess, onError, debounce?, when? })`: a resource per field, whose loader receives an `abortSignal`. It runs only while the field is valid by its synchronous rules (`syncValid`: no synchronous error on the field, including those a schema of an ancestor places on it, nor on any field below) and neither hidden, disabled, read-only nor orphaned (`shouldSkipValidation`); otherwise its parameters are `undefined` and the resource goes idle: it discards what the load in flight answers, but does not abort it (`loadEffect` returns before `abortInProgressLoad`), so the server keeps working. A new parameter aborts the previous load; an item removed from its array (`applyEach`) has its load aborted. `debounce` lets the first value through at once, then waits. A Standard Schema that answers with a promise is itself such a resource: an asynchronous schema never holds back another asynchronous validator. `pending` holds the field, its ancestors' summary and the loads below it. `debounce` delays the parameters.
- **TanStack**, `onChangeAsync({ value, fieldApi, signal })` and `onChangeAsyncDebounceMs` (0 by default, still a `setTimeout`): one `AbortController` per validator, aborted when the next run starts; a run aborted resolves to nothing. It runs only when the synchronous validators of the same event found no error, unless `asyncAlways`; when they find one, the run in flight is aborted. A field unmounted aborts its runs. `isValidating` turns true before the delay, so a field waiting for its debounce is already validating; but it counts its runs down when an aborted run rejects, as `fetch` does, so that after two changes it says it is not validating while its last run is in flight. A rejected promise becomes the field's error, the rejection itself.

## Options

1. **Native, or do nothing.** The platform has `AbortController` and `AbortSignal.any`, and constraint validation per input with no asynchronous check. Without the option, an application writes a Standard Schema whose `validate` returns a promise: it gets the generation of ADR 0043, but no signal, no abort when an item leaves, and its server is called on values its other schemas reject. Rejected: §7.11 asks for the signal and the abort.
2. **A wrapper of the Standard Schema interface that adds the signal** (`withSignal(schema)`). The interface would carry an option no engine reads, and the issues of the application would go through `issue.external`, losing their code. Rejected.
3. **An option `validate(raw, { signal, path })` on every node, returning a list of issues or a promise of one (kept)**, with the choices below.

When a validator runs:

1. **Always**, as TanStack's `asyncAlways`. A server is called on every value a schema already rejects, and its answer is shown beside the schema's. Rejected.
2. **When the node's own schema accepts its value.** Cheap, but the pilot describes a step by one schema of the whole step: a check of a SIREN on the server would run on every malformed SIREN the step's schema rejects. Rejected.
3. **A run starts once no schema can still place an issue on the node or below, and counts until a schema does (kept)**: it starts when every schema of the node, of its descendants and of its ancestors has answered for the value it reads, none with an issue on the node or below; it counts until the raw value or the lives of the items that hold the node change, a schema places such an issue, or the node leaves the form. A schema that has yet to answer neither starts nor drops a run: under a schema of the whole form that answers later, each keystroke in another field makes that schema pending again, and the first version, which closed the gate then, aborted the check of a SIREN and asked again for the same value at every keystroke, so that a user typing elsewhere kept it from ever answering, and its message came and went (the contradictor below). Angular's `syncValid`, with the schemas that answer later counted before a run starts, since their issues may land on the node; validators never wait for each other, so that a group's check and its fields' checks run together, and no validator can wait for itself.

What a validator reads and answers:

- **The node's raw value (kept)**, as its schema reads it and as both references read the model, so that an index in the path of an issue names an item of the value it read (ADR 0044). The parsed value would make indexes ambiguous: a schema of a list may give back anything. A validator that wants a schema's normalization calls `parse` itself.
- **`{ signal, path }`**: the signal of this run, and the path of the node, so that one function serves every item of a list and knows which one asks. The node itself is not handed over: a computation of the graph calls the validator, which must not read the graph (ADR 0042), and a node invites reading it.
- **`Issue`s of `@yaltaan/core`, their paths from the node (kept)**: one shared model, codes and parameters kept, placed as a schema's are (the deepest node the path names, an index replaced by the item's `{ key }`). An empty list is a success. A promise that rejects places `form.validation_failed` on the node, the reason as `cause`, as for a schema; an answer that is not a list of issues places it too, that answer as `cause`, which a new error would not keep equal from one run to the next; a validator that throws at once stays thrown: that is a bug.

The signal and the generation:

- **The run is the generation (kept)**: what a run answers counts only while that run is the node's last one and the node is in the form, so that a stale answer, or one that comes after its abort, is never delivered, whatever the validator does with its signal. A thenable that calls back twice is taken through a promise, which keeps the first.
- **A run is aborted when it stops counting before the form has received its answer, and only then (kept)**: its raw value changed (seen when its node is next read), a schema placed an issue on the node or below, or its node left the form, an item removed from its array, itself or an ancestor. The signal aborts on the next microtask, out of any computation of the graph or write: the first version aborted in the computation that asked again, where a listener of the signal that read the form threw, which Node reports as an uncaught exception.
- **Lazily, as every state (kept)**: a validator is asked only when a state that needs its answer is read, and a run whose value changed is aborted when the node is read again, which a view watching any state of the node does after every write. Aborting on every write, read or not, would need a listener per run in flight, which a computation cannot add (ADR 0042), and a walk of the ancestors at every write.
- **A removed item asks nothing (kept)**: its validators are aborted and stay idle, no state of the form reads it; given back by `reset()`, it asks again. The key of its life is a source per item that a validator sits under, built then, or when the item leaves a form that has validators: the first version built it only for the validators wired so far, so that a validator built later below a removed item, by a write into it, ran.

What is not in the form:

- **No delay option.** Each new value aborts the run before, so a validator that first awaits a delay honouring its signal is debounced, in one line, and its node is pending during the delay, as TanStack's is. T3.7 a (`core/async`) may give that delay; the form does not need it before, so T3.7 a stays in its lot.
- **No signal of the form's life.** An application that discards a form while a run is in flight combines the run's signal with its own, `AbortSignal.any([signal, destroyed])`: the platform already composes them.
- **Disabled nodes still validate**: what a disabled node does to its issues is decided on the pilot (T2.4 e, ADR 0043), validators included; Angular skips them.
- **No narrowing of what asks again**: a validator reads its node's whole raw value, so a check of two fields of a group asks again on any change in the group; Angular's `params` and TanStack's `onChangeListenTo` narrow it. A validator on a smaller group, holding the fields it reads, does the same; the pilot may reopen it.
- **Nothing to await at submission**: `submit()` returns while a validator runs, with the issues known so far, as for a schema (ADR 0043); TanStack's `handleSubmit` awaits its validators. A view waits for `pending` to turn false.

## Measurements

On 2026-11-11, Ubuntu 26.04 x64, Node 24.21.0, TypeScript 7.0.2 and 6.0.3, on cores shared with another project's load:

- **Size**, `node scripts/size-report.ts`: `yaltaan/form-realistic`, which holds no validator, 5,950 / 5,978 → 6,488 / 6,524 B brotli (esbuild / Rollup), and `yaltaan/form-array` 7,526 / 7,572 → 8,145 / 8,198 B, under their hypotheses of 7,000 and 8,200 B: 2 B are left to the second. The fixes of the review below cost 185 B at first and took `form-array` over its budget; folding the schemas above into the doubt of a node, one derived node fewer, marking an item out when its life is first built outside its array instead of walking the description, and a test left redundant, brought it back under. A form pays the validators' code whether it uses them or not: an option, unlike `array`, cannot carry its code to the forms that import it; the module of nodes alone, minified, goes from 2,664 to 3,258 B brotli. Moving validators behind an export of their own was rejected: every application would wrap its validators to spare the bytes of those that have none.
- **Type cost**, `node scripts/type-cost.ts`: the usage `form`, which holds no validator, 17,470 / 17,494 → 17,862 / 17,886 instantiations under TypeScript 7 (exact / loose) and 12,037 / 12,058 → 12,165 / 12,186 under 6.0, adding 17,280 and 11,580 to the fixture, under its ceilings of 17,700 and 12,300; `form-array` 19,158 / 19,182 → 19,574 / 19,598 and 12,535 / 12,556 → 12,684 / 12,705, under 21,200 and 13,900; check time +613.7 % and +635.9 % with each usage in every file, budget +900 %. The first version added 622 and 358 to `form`: the options of `group` read the raw type through `NoInfer`, which `RawOf`, a conditional type, does not need (a test shows that a validator's parameter still cannot change the children's type); a property of a function type instead of a method costs fewer, but checks its parameter contravariantly, so that a field with a validator would no longer be a `Spec`.
- **Heap**, `--expose-gc`, 20,000 fields of a flat group: a field without a validator 1,021 B built, 1,712 B once every state is read (1,020 and 1,712 before); with a validator answering at once, 1,167 and 2,502 B.
- **Laws** (`properties.test.ts`): the naive model keeps, for each validator, the run that counts and applies the rules at each look: dropped when a schema places an issue, when its node is out of the form, or when its raw value or the lives of its items differ from those it was asked for, and then expected aborted if it was still in flight; a new run when none counts, no schema may still mark the node and it is in the form; a schema that has yet to answer changes nothing. `fc.scheduler()` releases the answer of one run at a time, the one it picks, aborted ones included, and every run left at the end, a look after each; each signal is checked a turn of the event loop after each look. 400 programs of every shape (one run: 753 runs, 132 aborted, 30 by a removal, every aborted run's answer released afterwards and ignored, 574 issues of validators looked at, 436 looks at a run kept while a schema had not answered), 200 crowded with moves, and 200 of an array whose items each hold a validator, with removals, restores and releases (2,185 runs, 852 aborted, 282 by a removal, 338 items holding a validator given back), in about 3.8 s. Found while writing: a validator answering something else than a list made a new `TypeError` each time, which `equal` compares by identity, so that the same failure told listeners again: the cause is now the answer itself; and a node with nothing to read held its validator back for good, `Math.max()` of nothing being `-Infinity`.
- **Examples** (`validate.test.ts`, 25): the signal and the path, the gate by a schema of the node, of an ancestor, of a node below and one that has not answered, a write elsewhere under a schema that answers at once and under one that answers later (no run aborted or asked again, no message that comes and goes), a change of the node's own value under the latter, a value set back before the node is read, laziness and its late abort, issues placed below and through an array, failures, an answer that throws when read, a thenable that calls back twice, removals of items and of the items they hold, a validator built below a removed item, a removal and a restore in one batch, a move, a delay that debounces, a validator that never settles, a schema of `@yaltaan/schema` in front, unhandled rejections checked in a process of their own, a listener of the signal that reads the form, types.
- **Mutations by hand**, each on a copy, restored by copy, against an unmutated control that stays green: 27 on the first version, among them each abort left out (a new question, a removal, the items a removed item holds, the items above), a run cleared by an older one, the gate without each of its parts, issues dropped or not placed, an empty list as a failure, a stale answer standing in, a removed item that still asks or never comes back; 26 caught, 1 equivalent survived; against the laws alone, the restore of a removed item first survived, caught only by an example: the third law above was written for it, and catches it. 16 on the version after the review (a pending schema that drops or starts a run, an answer that throws uncaught, a life built below a removed item in the form, the abort in the computation, the empty maximum, an issue that only holds back, the doubt blind to the schemas above or to the nodes below, a new value or a given-back item that keeps its run, an older run clearing a newer one's flight, a removal of the item only or without its abort, a removed node that starts a run, an array's doubt not rewired): all caught; a guard an earlier pass found unreachable was removed. The laws alone catch 13 of them; the other three (an answer that throws when read, a write into a removed item, the turn on which the signal aborts) are written as their blind spots, and caught by examples.
- **References** (`tests/interop/form-async.mjs`, outside the gate): the same runs on Angular Signal Forms 22.2.4, TanStack Form 1.33.5 and the form. They agree that a new value aborts the run in flight and that its answer never counts, that a value a synchronous rule or a schema above rejects asks nothing, that a removed item aborts its run, and that only the last value outlives a delay. The form departs on purpose: nothing runs before a state is read (Angular asks at once, TanStack at the first change); a rejection is `form.validation_failed`. Two defects of the references were found and are asserted there: TanStack says it is not validating while its last run is in flight once an aborted run rejected, as `fetch` does; Angular does not abort a load whose value turned invalid, it only discards its answer.

- **Contradictor**: a fresh reviewer, given only the question and the code (187,908 tokens), ran its own probes and 29 mutations of its own, all caught. Verdict: accept with fixes, all applied before this record was committed:
  - a schema that answers later aborted and asked again every validator below it at each write elsewhere: 11 runs and none completed while the user typed in another field every 30 ms, and the message of a SIREN came and went. The rule of option 3 above;
  - an answer whose reading throws (a getter, an iterator) left the node pending for good and a rejection unhandled: it is now `form.validation_failed`, the error as `cause`;
  - the gate was red on its copy: the declarations named a global `AbortSignal` that an application with neither library cannot resolve (now declared empty, merged by either library), the reference, the baselines and these measurements were not written yet;
  - the documentation said a validator is asked only after its raw value changed, and that a run that answered is never aborted: it now says when a run counts, and that an answer the form has not yet received may still be aborted;
  - a validator built below a removed item, by a write into it, ran: such an item is marked out of the form;
  - an abort listener that reads the form threw in the computation: the signal aborts on the next microtask;
  - not applied, with the reason: the method's parameter is checked both ways, so that `field<string | number>` accepts a validator of strings, as `equals` already does: a function property would make a field with a validator no longer a `Spec`; the bytes a form without a validator ships, which an option cannot spare (above); a write at the leaf of a chain of d groups, each with a schema, under a validator at the root costs O(d²), 279 ms for 20 writes at 800 levels, the doubt of each level reading the issues of every schema above it: no real form nests that deep.

## Decision

Option 3.

- **API**: `validate(raw, validation)` on the options of `field`, `group` and `array` (`NodeSpecOptions`, whose second parameter is now the raw type), returning `readonly Issue[]` or a promise of it; `Validation` holds `signal` and `path`; both exported. `checkOptions` refuses a `validate` that is not a function.
- **When**: a run starts once no schema of the node, of its descendants or of its ancestors is pending or has placed an issue on the node or below; it reads the raw value. It counts until its raw value or the lives of its items change, a schema places such an issue, or the node leaves the form; a pending schema neither starts nor drops it.
- **Abort**: a run that stops counting is aborted, on the next microtask, unless the form has received its answer.
- **Issues**: placed from the node as a schema's are; the node's issues are its schema's while there are any, its validator's otherwise; `form.validation_failed` for a rejection or an answer that is not a list of issues.
- **Budgets**: unchanged; `yaltaan/form-realistic` keeps 7,000 B and `yaltaan/form-array` 8,200 B, the usages `form` and `form-array` their ceilings.
- **Declarations**: the form declares the global `AbortSignal` empty, so that its declarations compile in an application that reads neither the DOM's library nor Node's; where one is read, it merges in whole.

## Consequences

- A node with a validator holds about five more nodes of the graph (the question, the answer, the combined answer, its placement, and whether a schema marks it or may still); every node below it, one more; an item a validator sits under, one source. A form without a validator holds none of them, but ships their code, about 540 B brotli.
- The validator runs in a computation of the graph: it must not read or write the form's graph; what listens to its signal runs on a later microtask and may.
- A run whose node is not read again after its value changed is not aborted until the node is read, or leaves the form; its answer is never delivered.
- The issues of a node come from its schema while it has any, from its validator otherwise: a node never shows both, since its validator waits for its schemas.
- What the judges do not see: what a validator's listeners do with the graph, a validator that never settles (its node stays pending, as with a schema), the time a run takes, and disabled nodes, whose validation T2.4 e decides.

## Review condition

The pilot needing the parsed value in a validator, a delay of the form's own, a signal of the form's life, or a validator that waits for those below it; the budgets T2.6 sets leaving no room for the bytes of validators in forms that have none; T2.4 e deciding that a disabled node does not validate; Angular or TanStack changing when their asynchronous validators run.

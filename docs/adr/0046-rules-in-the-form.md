# ADR 0046 — Rules read by the form: a node per rule, reading only its paths, and `required` derived from them

- Date: 2026-11-12
- Status: accepted (design choices delegated by the owner, reported for review; `@experimental` until the go/no-go decision of T2.7 and the frozen contracts)

## Context

ARCHITECTURE.md §7.11 asks for "targeted revalidation through the dependency graph of `@yaltaan/rules`, never global by default", and §7.10 that whether a field is required be a derived state, `requiredPaths(rules, values)`, never a mutation of other rules. ADR 0043 left both to T2.4 d: a rule reaching the form through `refine` is a Standard Schema, whose issues arrive as `issue.external` with the code as message, and which reads the whole value of its node on every change. T2.4 d asks that each rule be a node of the graph that reads only its declared paths, that its issues keep their code, that `required` be derived from `requiredPaths`, and that a write check again only the rules that read the field written, counted call by call; and that the pilot's scenarios pass through the form. A new option of every node and a new state are public API: they need a record.

The references, read in their shipped code and run (Angular Signal Forms 22.2.4, TanStack Form 1.33.5, on 2026-11-12):

- **Angular** writes a rule across fields as a validator of one field that reads others through `valueOf(path)`: each validator is a computed signal, so that it runs again only when a signal it read changes, the read deciding, not a declaration. `required(path, { when })` gives a field's `required()` state, from the same condition as its error. A validator of a field reads other fields wherever they are; the rule has no declared shape, and the same rule cannot run outside Angular.
- **TanStack** writes it as a form-level validator, `validators.onChange`, run on every change of any field, all its rules in it, or as a field validator with `onChangeListenTo`, the fields that run it again listed by hand. It has no `required` state.

## Options

1. **Native, or do nothing.** Rules through `refine`, as ADR 0043 left them: every rule runs again on every change of its node, its issues are `issue.external`, and nothing says what is required. Rejected: §7.11 asks for targeted revalidation and codes kept.
2. **A wrapper, `ruled(spec, rules)`, that carries the code of rules.** A form without rules would not ship it; but every node already takes its schema, its condition and its validator as options, and every application with rules would wrap. Rejected for the reason ADR 0045 gave for validators.
3. **An option `rules` on every node, each rule a node of the graph whose dependencies are the nodes its declared paths name (kept)**, with the choices below.

What a rule reads:

- **The raw values of the paths it declares, and nothing else (kept)**: the paths are read against the description when the form is built, so that a typo fails then, as a condition's does (ADR 0044): a group's segment names a child, any segment of an array stands for every item, and a path that reaches a field reads the field whole. The rule is handed a value built from those nodes only, so that it cannot read what it does not declare; a rule that would, as one an application writes wrongly, meets `undefined` there, which `assertDeclaredReads` already tells in its tests. Reading the whole raw value of the node, as `refine` does, was rejected: a rule over emails would run again at each letter of a name.
- **Raw values, not parsed ones (kept)**, as schemas and validators read them (ADR 0043, 0045): a rule has to run while a schema has not answered, and a parsed value is an error then.
- **An index in a declared path reads every item (kept).** Which item stands at index 0 changes with each move, so the form reads the field in every item and the rule picks the one at that place; reading only the first item would need a node rewired at every move for the place, not for the item. `anyElement` and a `{ key }` segment read every item too.
- **Through an array, a node per array and per what the rule reads of an item (kept)**, the list of what it reads of each item, rewired with the items, as the states that follow them are (ADR 0044), so that the rule itself never needs rewiring; nested arrays nest their views. Rewiring the rule's own dependencies would need every array on its way to know it, and would leave a rule registered on the arrays of removed items.
- **A sub-form left empty is an object, as `checkRules` reads it (kept)**: a group a rule reads whole is its raw value, never a blank, so that the form and a server that runs the same rules on the same value give the same answer. The first version read a group none of whose fields held a value as `undefined`, so that `requiredIf(…, [['billing']])` would mark an empty billing address in a form as it marks an absent one in the values an application submits; the contradictor below refused it: with `mutuallyExclusive([['a'], ['b']])`, an empty group `a` and `b` filled, the form passed what `checkRules` refused on the raw value and on the parsed one, so that a client accepted what its server would refuse, and an empty row counted as something entered for its group but as absent for a rule over its list. What a form does with an empty sub-form, what it submits and what rules read of it, joins what it does with a disabled one (T2.4 e), where the parsed value is decided: changing what is blank in `@yaltaan/rules`, for every engine, is one of the options there. Three scenarios of the pilot wait for it.

When a rule is checked:

- **Again only once a node it reads changes (kept)**: a field's raw value by `Object.is`, a group's when one of its fields does, an array's or a view's when its items or what it reads of them do. The rule runs in a computation of the graph, once per change, and only when a state that needs it is read: the issues of a node at or below, the parsed value, `pending` through a validator it holds back, `required`. What it says and what it requires are two nodes, so that reading one does not run the other.
- **Each rule a node of its own (kept).** One node for all the rules of a node would run every rule on every change; a node per rule costs one derived node per rule, two with `required`, and one per array view and per what a rule reads of an item, against one per node. A node of values between a rule and its paths, shared by `check` and `required`, was the first version: with the empty group read as `undefined`, it kept that value across a change and checked nothing, which the laws below found; each answer of a rule now reads its paths itself.

What its answer does:

- **Its issues keep their code and data (kept)**, placed as a schema's are: the deepest node their path names from the rule's node, an index in the list the rule read replaced by the item's `{ key }`, a `{ key }` naming an item by the key its value holds at `identity`, as the rule read it, or by the form's key without it. On a node, the issues of its schema or validator come first, then its rules', each rule's in order, and the outermost node first.
- **`required` (kept)**: a node is required when `required` of a rule of the node or of an ancestor gives a path that names it, placed as an issue is. Angular's `required()` is the reference; it shows, and the rule decides: a required field already filled stays required.
- **A warning blocks nothing (kept)**: an issue of severity `warning` is shown, and neither makes the parsed value an error nor holds a validator back, as `@yaltaan/rules` says of `checkRules` and `refine`. It applies to every issue of the form, a validator's included, where ADR 0043 and 0045 treated every issue alike; no schema gives warnings.
- **An issue of a rule on a node or below holds its validator back (kept)**, as a schema's does (ADR 0045, extended): a SIREN that a rule finds blank or malformed is not sent to the server, and a run in flight when a rule marks the node is aborted. Rules answer at once, so they never make a validator wait.
- **What a rule throws is thrown by every state that depends on it (kept)**, as a schema that throws at once: that is a bug.

## Measurements

On 2026-11-12, Ubuntu 26.04 x64, Node 24.21.0, TypeScript 7.0.2 and 6.0.3, on cores shared with another project's load:

- **Size**, `node scripts/size-report.ts`: `yaltaan/form-realistic`, which holds no rule, 6,488 / 6,524 → 6,937 / 6,966 B brotli (esbuild / Rollup), under its hypothesis of 7,000 B; `yaltaan/form-array` 8,145 / 8,198 → 8,748 / 8,807 B, over its hypothesis of 8,200 B: a form pays the rules' code whether it has rules or not, as it pays the validators' (ADR 0045). The first version weighed 6,982 / 7,011 and 8,714 / 8,783 B: without the empty group read as `undefined`, with the index of keys in `named` (below) and `required` built when first read, the figures above. One factory for what a rule says and what it requires saved 58 B before compression and cost 3 to 9 B brotli: not kept. `required` built when first read costs 6 to 17 B and saves 1,370 B of heap per item below: kept.
- **Type cost**, `node scripts/type-cost.ts`: unchanged by the rules, the usages `form` and `form-array` holding none; the move of the types to `types.ts` took 20 instantiations off each under TypeScript 7 (`form` 17,862 → 17,842, `form-array` 19,574 → 19,554) and 5 under 6.0.
- **Heap**, `--expose-gc`, bytes per field or per item, built / once raw, issues, touched, disabled, pending and `required` of every field and the parsed value of the form are read: a field of a flat group of 20,000 without rules 852 / 917 B, unchanged; an item of five fields under a group, 1,000 items, without rules 5,966 / 6,411 → 5,973 / 6,422 B; with an `allOrNone` of two of its fields on each item, 9,751 / 13,299 B (11,112 B built while `required` was built at once): each node below a node with rules holds a node of issues and, once read, one of `required`; each rule one or two. A field of a flat group of 20,000 with 10,000 rules at the group: 1,898 / 2,714 B.
- **Cost of a write**: placing issues that name items by `{ key }` looked for each key item by item, a `Set` per comparison: with every product of a list kept by key marked by a rule of `each`, a write took 1.31, 3.34, 12.46 and 44.42 ms at 125, 250, 500 and 1,000 products (the contradictor's measure), quadratic. `named` now builds the index of the keys of a value once, the first item holding a key winning as `findIndex` did: an example compares 125 and 1,000 rows, best of five rounds, and fails past 24 times. A write re-places the issues of every rule of the node that holds the rule it changes, linear in their number.
- **Laws** (`properties.test.ts`): the naive model gives each rule, at each look, the raw value of its node, places what the rule says and requires from what it read, and expects one call of `check`, and of `required`, for each rule of a node in the tree, or out of it but still watched, whose fields at the end of its paths or the items of an array on its way are not those of its last call: a rule on the state, never a copy of the dependencies. Rules are drawn on every node of every program, reading nodes at or below it, every item, the item of an index, a place in a field's list; they place issues on what they read, warnings among them, on their node, on a path that names no node, items by index, by the key their value holds at `k0` when the rule reads it, or by a number; `required` is compared on every node. A fourth family, 150 programs, holds rules on the root, on an array kept or not by a key, on its items, beside a group and a field whose validator a rule may hold back. One run of the four families (400, 200, 200 and 150 programs): 2,271, 934, 1,716 and 4,812 calls of rules checked one by one, 7,870, 3,742, 4,340 and 21,769 issues of rules and 1,463, 820, 1,256 and 4,185 warnings looked at, 3,063, 1,370, 1,849 and 7,120 nodes required, and in the fourth family 6,179 looks at a validator held back by rules alone; the four take about 20 s. Found while writing: the law's own rule read a key it did not declare; the model expected a call where the first implementation kept a value unchanged; the model, at first, found an item by a key its rule had not read; and the first two families went red on a seed of their own once rules were drawn in them: a removed item still watched has its rules checked again when a write of the same batch reached it, as the model already said of schemas.
- **Pilot** (`examples/pilot/live.test.ts`): the pilot written with the form (`live.ts`), its 33 rules at the root, the postal code of an address left empty not checked, as an application writes it for a form, whose sub-forms are always there, and the schemas of `form.ts` on the nodes they read, the fields of the billing address and of the parent company through `optional`; 43 of the 46 scenarios pass through it, their issues by code and path, items named by the key their value holds, the derived values and what reaches the server as `form.test.ts` judges them. The other three wait for what a form does with an empty or a disabled sub-form, and must fail until then: an empty billing address and an empty parent company are not marked as required, the form accepting what the server's schema refuses, and a parent company unchecked after being filled still shows its issues. Fourteen writes across the steps each check again exactly the rules that declare the field written, once; `required` equals what `requiredPaths` says of the raw value, node by node, on all 46 scenarios.
- **Examples** (`rules.test.ts`, 20): call counts on a group, a list, a move, an insertion, a removal and an index; what a rule is handed; a group read whole, the same answer as `checkRules`; codes, data, order and placement; `required` against `requiredPaths`; laziness; a rule that throws; warnings; a validator held back and aborted; paths refused when the form is built; rules of an item, of an array, `each` by a business key; a key that names no item of the list read, and one two items hold after an edit; a rule that reads nothing; 200 writes into one item of 250 and of 2,000 items; keyed issues at 125 and 1,000 rows.
- **References** (`tests/interop/form-rules.mjs`, outside the gate): the same three rules (a field required in France, a contract number and its date together, unique emails) in Angular Signal Forms 22.2.4, written with its own validators, in TanStack Form 1.33.5 through `refine`, and in the form; the same writes. They agree on each field's issues and on `required`. Checks after the four writes, by rule (`siren`, `contract`, `emails`): Angular 2, 2, 6, since its uniqueness validator reads the whole list and runs again when a contact's name changes; TanStack 5, 5, 5, every rule on every change; the form 2, 2, 2.
- **Mutations by hand**, each on the file, restored by copy, against an unmutated control that stays green (376 tests of the form): 27 on the first version, and 26 on the final one, among them an array read whole, a rule that reads nothing given the node, a deeper path not covered by a whole read, a path not stopped at a field, every child of a group read, issues or required paths not placed from the node or from what the rule read, rules that hold no validator back, a warning that does, a warning that blocks the parsed value, rules placed before the schema, `required` by every rule or by the node's own only, an ancestor's rules dropped, a view not rewired, not named or built anew at each read, the rules of a node with a schema dropped, a check kept by equal issues, an options check that lets anything through, a key named by its last item, key indexes kept by the items instead of the value, keys not bounded, keys looked for item by item: all caught. The laws alone catch 21 of the final 26; the examples the rest (a rule that reads nothing, the options check, long keys, the cost of finding keys, a key two items hold after an edit), the last of which survived every test at first and now has its example.
- **Contradictor**: a fresh reviewer, given only the question and the code (201,066 tokens, 28 minutes), ran its own probes and 41 mutations of its own, every one that changes behaviour caught, two controls equivalent by construction. Verdict: accept with fixes:
  - writes cost quadratic time on lists kept by key (above): fixed, with its example;
  - a rule with no path on an array of groups threw on its first item, the write half made: a rule that reads nothing is now handed nothing, with its example;
  - the empty group read as `undefined` made the form disagree with the same rules on the same value: dropped (options above), three scenarios of the pilot now waiting;
  - the gate was red on its copy: ticket names in comments, `docs/reference/` and the baseline of the type cost not written, `dist/types.js` in the tarball since the move: all fixed;
  - `form-array` over its budget: the decision below;
  - the guide said a `{ key }` names an item by its index when the array has no `identity`: it stays on the list, and the guide now says so;
  - not applied, with the reason: a required path past the last item marks the list, as an issue past it does (ADR 0044); moving the rules out of `node.ts` so that a form without rules ships none of them needs a wrapper (option 2); a `check` that answers something else than a list throws, where a validator's answer becomes `form.validation_failed`: a rule is synchronous code of the application, and a bad answer is a bug, as a schema that throws at once (ADR 0043).

## Decision

Option 3.

- **API**: `rules` on the options of `field`, `group` and `array` (`NodeSpecOptions`), the `Rule`s of `@yaltaan/rules`, their paths from the node; `required`, a `ReadableNode<boolean>` on every node. `checkOptions` refuses rules that are not a list of objects with `reads` and `check` and, if given, a `required` function; `createForm` refuses a path that names none of its nodes.
- **Reads, checks, issues, `required`, warnings, validators**: as kept above.
- **Budgets**: `yaltaan/form-array` 8,200 → 9,300 B, a hypothesis still, the measure under Rollup plus a twentieth, rounded up to the hundred, until the pilot is measured against Angular Signal Forms alone (T2.6); undone by one line of `bench/size/budgets.tsv`. `yaltaan/form-realistic` keeps 7,000 B, 34 B above its measure; the usages of the type cost keep their ceilings.

## Consequences

- A form without rules holds none of their nodes, but ships their code: about 445 B brotli, 605 B with arrays, the view of an array being in the module only arrays reach.
- The form's source has a fourth module, `types.ts`, the public types moved out of `node.ts` as they were, outputs and bytes unchanged, so that the module of nodes keeps under its 1,200 lines.
- `targets` of a rule is not read: an issue goes where its path says, and a required path past the last item marks the list.
- An empty billing address or parent company is not marked as required by a rule on the group: the form version of the pilot reads their fields through `optional`, so that it accepts an empty one its server's schema refuses, until T2.4 e decides what a form submits for an empty sub-form.
- A `disabled` condition still reads raw values, a group as its object: what a disabled node does is T2.4 e's, which may align it.
- Each node below a node with rules holds a node of issues, as below a schema, and one of `required` once read: a form with rules at its root pays about 300 B per node for each.
- What the judges do not see: blank values other than `undefined` in the laws, rules that throw, the options check and a rule that reads nothing (examples), a rule whose `check` reads what it does not declare (the form hands it nothing there, `assertDeclaredReads` is its test), the time a rule takes, the cost of a write beyond the two scale examples, and what a disabled or empty sub-form does to rules, which is T2.4 e's.

## Review condition

The pilot (T2.5, T2.6) needing a rule that reads parsed values, an index read for one item only, or the same rule run on a subset of a list; T2.4 e deciding what a disabled or an empty sub-form does to rules and to what a form submits, or `@yaltaan/rules` counting an empty object as blank; TC39 Signals reaching Stage 3, whose computed signals track what they read, as Angular's validators do; the size of a form without rules over a budget T2.6 sets.

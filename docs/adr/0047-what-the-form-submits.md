# ADR 0047 — What the form submits: a node disabled or hidden, or an optional sub-form left empty, is left out, and every check reads what is submitted

- Date: 2026-11-14
- Status: accepted (`@experimental` until the go/no-go decision of T2.7 and the frozen contracts)

## Context

ADR 0043 gave every node a `disabled` condition and left what it does to T2.4 e: "What it does to issues, to the parsed value and to dirty and touched, where only Angular has an answer, is decided on the pilot, whose billing address and parent company are the cases." ADR 0046 kept a sub-form left empty as an object for the rules, as `checkRules` reads it, after a first version that read it as `undefined` let a form accept what its server refused on the same value; it sent what a form does with an empty sub-form, what it submits and what its rules and conditions read, to the same step, with three scenarios of the pilot waiting for it: an empty billing address and an empty parent company not marked as required, and a parent company unchecked after being filled still showing its issues. ARCHITECTURE.md §7.11 lists `readonly` and `hidden` among the derived states, with no meaning yet. New options, new states and a changed parsed value are public API: they need a record.

The references, read in their shipped code and run (Angular Signal Forms 22.2.4, TanStack Form 1.33.5, on 2026-11-14):

- **Angular** has the three conditions, each a `when` on the model, inherited by every node below. `hidden`, `disabled` and `readonly` alike skip validation (`shouldSkipValidation`): the node's errors are empty, the errors that a validator of an ancestor targets at it are dropped, its status is valid, and an asynchronous validator is not run. They mask `dirty` and `touched` (`isNonInteractive`), and `submit` does not mark them touched. `required()` is not masked: a disabled field whose `when` holds is still required. The value stays in the model, which is what the submit action reads: a hidden or disabled value is sent unless the application removes it.
- **TanStack** has none of the three: an application hides a field by not rendering it, and its value and validators stay.
- **The platform**: a disabled control is barred from constraint validation and left out of the form's data; a read-only control is barred from constraint validation and submitted; the `hidden` attribute changes neither.
- **Empty sub-forms**: Angular and TanStack hold every input of a sub-form, so an empty one is an object of empty strings, which a rule of `@yaltaan/rules` reads as filled: `requiredIf(…, [['parent']])` never fires in either engine (tests/interop/form-conditions.mjs).

## Options

What a disabled or hidden node does:

1. **Native, or do nothing.** `disabled` changes nothing but its own state, as ADR 0043 left it: the parent company unchecked still shows its issues and its values are sent, and every application filters both by hand. Rejected: the pilot's third scenario fails, and an application writes what Angular writes for it.
2. **Angular's: the value kept, the node's checks skipped, the issues placed on it dropped.** What the form accepts then differs from what a server running the same schema and rules accepts on what it receives: the hidden values are sent, so that a rule over them refuses on the server what the form let through, and a rule reading a hidden value shows an issue on a visible field the user cannot explain (`mutuallyExclusive` of a SIREN and a foreign registration hidden in France). The pilot keeps its derivation that drops the unchecked parent company. Rejected.
3. **The platform's, extended: a node disabled or hidden is left out of what the form submits, its checks are not asked, and every check that remains reads what the form submits (kept).** A value the user cannot see or use is neither sent nor checked; a rule and a schema of an enclosing node read the submission, so that the form says what a server checking what it receives says; and nothing is hidden: an issue a remaining check places on a node left out, a field the application requires and hides, shows on it and holds the submission back.

What a read-only node does:

1. **Angular's and the platform's: submitted, not checked.** A value the form sends is then never checked by the form, and a schema of its own gives no parsed value. Rejected.
2. **Submitted and checked, `touched` masked, `dirty` shown (kept).** It is submitted, so it is checked as the server will check it, and a change of its value, which the application makes, is a change of what is submitted; the user cannot act on it, so it is never touched. The first version masked `dirty` too, as Angular does: the reviewer below found a read-only total changed and submitted while nothing was dirty, against what `dirty` is for, an "unsaved changes" warning.

What an empty sub-form does:

1. **Native, or do nothing.** An empty sub-form stays an object, as ADR 0046 left it, and the pilot's form reads each field of its billing address and parent company through `optional`, so that an empty one passes; then an empty one is never required, and a started one whose street is left `undefined` passes where the server refuses. Rejected.
2. **`@yaltaan/rules` counting an object whose values are all blank as a blank.** It would make `requiredIf` fire on an empty sub-form in Angular, TanStack and the form alike; but it changes the contract of ADR 0034 for every engine, a decision of its own, the server still receives an object its schema refuses field by field, and a sub-form that is required is told apart from one that is optional only by the schema. Not taken: no question is needed, since the next option settles the pilot without it, and it stays open for T5.6.
3. **An option of the group, `optional: true`: while none of its fields holds anything but a blank (`undefined`, `null`, `''`, an empty list, as ADR 0034 reads one) nor any of its arrays an item, the group is left out of what the form submits (kept).** It is what `optional(address)` says on the server: absent. A rule then finds it blank, as `checkRules` finds the absent key in the values a server receives; its fields are not checked; once anything is entered, it is present and each field is checked by its own schema. Automatic for every group was rejected: a required sub-form left empty would read as absent, `schema.missing` on the group instead of each field's issue.

What the states say:

- **`dirty` follows what is submitted: false on a node disabled or hidden, shown on a read-only one; `touched` false on all three (kept)**, Angular masking both on all three; a field touched or changed while disabled shows it once enabled again, where Angular does not mark it on submission: the form's states follow values and marks, not events. An array compares its raw value with its initial list (ADR 0044), fields left out included: a disabled field of a row changed by the application leaves its row and group clean and makes its array dirty; masking it needs a node per row, ticket T6.7.
- **`required`: what the rules say on what is submitted (kept)**, not masked, as Angular and the platform keep it.
- **`parsed` of a node left out: an error, with the issues known (kept)**: it submits nothing; a hidden root, or an optional one left empty, submits an error without issues. In its group's read value, its key holds `undefined`; in its array's, it is dropped. A key holding `undefined` rather than left out keeps the types simple, and `optional(…)` of `@yaltaan/schema` reads an explicit `undefined` as absent. The types say it by three signatures of `field`, `group` and `array`. The first, which a call takes when it infers its type arguments, reads its options as `FieldOptionsGiven`, `GroupOptionsGiven` or `ArrayOptionsGiven`: `Disabled` and `Hidden` are inferred from the type of the `when` of each condition given (`ConditionGiven`), `unknown` for none, and a group's `Optional` from `optional`; the node reads `Output` while both are `unknown` and `optional` is absent or `false`, `Output | undefined` otherwise, a condition or options of a wider type included. Its inferred type parameters come before `Output` and have no default, so that a call that writes its type arguments out (`field<string | null>(null)`) cannot take it, and takes one of the two others: options that hold neither `disabled` nor `hidden`, nor for a group `optional: true` (`Staying`), read `Output`; any other options `Output | undefined`. The first version matched a literal `disabled` or `hidden` first and everything else second, so that options of a wider type read `Output` where the value could be `undefined` (the reviewer's probes); a third overload closed it and cost about 1,400 instantiations and 60 to 100 points of check time on `form-array`; two overloads, the common case tried first, still cost +927 % against a budget of +900 % on a calm machine, since a call whose options leave a node out is resolved twice. One signature alone cannot tell a type argument written out from a condition absent, a default being the same in both, and would read `Output` there; inferring the whole condition rather than the type of its `when` costs more than the overloads, the paths it reads copied and widened at each call.
- **A condition reads raw values (kept)**, what the inputs hold: what is shown never depends on what is shown, and a box can hide the sub-form it belongs to without a cycle.
- **Whether a node is left out follows its ancestors and its own option only (kept)**: a condition of its own, or for an optional group what it submits. The first version derived it from what each ancestor submits, so that a write anywhere reached every node of a form holding one condition, and a condition that throws broke the issues of unrelated fields (the reviewer below).
- **The rules of a node left out are not asked (kept)**, as its schema: a server that runs the same rules under the same optional node (`refine(optional(…), rules)`) agrees; one that runs them from the root over an absent sub-form does not, which the documentation says.

## Decision

Options 3, 2 and 3.

- **API**: `hidden` and `readonly` on the options of `field`, `group` and `array`, conditions as `disabled` is, their paths checked when the form is built; `optional` on the options of `group`, refused on a field or an array; `hidden` and `readonly`, `ReadableNode<boolean>`, on every node; the types `Staying`, `ConditionGiven`, `FieldOptionsGiven`, `GroupOptionsGiven` and `ArrayOptionsGiven`; `field`, `group` and `array` with the three signatures kept above.
- **What is submitted**: nothing for a node disabled or hidden, or an optional group none of whose fields holds a value nor arrays an item; otherwise its raw value, a child left out holding `undefined`, an item left out dropped. A node is left out when it or an ancestor submits nothing.
- **Checks**: the schema, validator and rules of a node left out, and of every node below it, are not asked, and a validator's run in flight is aborted when its node is left out; every other check reads what the form submits; no issue is filtered.
- **States**: as kept above; whether a node is left out is a node of the graph only where its ancestors or its own option can leave it out.
- **Budgets**: `yaltaan/form-realistic` 7,000 → 8,100 B and `yaltaan/form-array` 9,300 → 10,000 B, hypotheses still, the measure under Rollup plus a twentieth, rounded up to the hundred, as ADR 0046 set the second, until the pilot is measured against Angular Signal Forms alone (T2.6); undone by two lines of `bench/size/budgets.tsv`.

## Consequences

- An application whose schema requires what it disables or hides sees the issue on that node and cannot submit: its schema says `optional` where the form may leave a value out. The scenario `form-realistic`, the usage `form` of the type cost and `form-states.mjs` were changed so.
- The pilot drops its own filter of empty addresses and its fields read through `optional`; its derivation that drops the unchecked parent company stays, since it shapes the values a server receives from the raw value, which the replay still reads.
- What a node submits and whether it is left out are nodes of the graph only where a condition or an optional group can leave something out: elsewhere they are the raw value and a shared `false`, so that a form without them holds no more nodes.
- A rule reads a node that may be left out through a node of its own, which keeps `ABSENT` while it is out: nothing below it reaches the rule then, and a write into a hidden sub-form checks no rule again.
- An item whose `identity` field is hidden submits no key: a `{ key }` of a schema or a rule that names it finds no item, and its issue stays on the array.
- Reading the issues of one field whose ancestor has a schema or rules composes what that ancestor submits, as it composed its raw value before.
- What the judges do not see: blanks other than `undefined` in the laws, a field that starts with `false`, the schema of a group with a child left out, an item left out of a list a schema names by index, a condition that throws, the types and the options check (examples, `conditions.test.ts`); the signatures under `exactOptionalPropertyTypes` off, which the gate does not compile, and with type arguments written out to the first one (`field<string, unknown, unknown>`), which nothing refuses; the `dirty` of an array whose rows hold fields left out (T6.7); the cost of a write beyond the scale example.

## Review condition

The pilot (T2.5, T2.6) needing a hidden value submitted, or a read-only value left unchecked; an application finding `undefined` keys in the read value harder than left-out keys; T5.6 deciding that `@yaltaan/rules` counts an object of blanks as a blank; the size of a form without conditions over a budget T2.6 sets; the go/no-go decision of T2.7.
